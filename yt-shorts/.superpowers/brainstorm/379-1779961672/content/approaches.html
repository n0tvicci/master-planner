API Structure — 3 Approaches

How the project_id and step endpoints relate. Pick the structure you prefer.

A — Project-Scoped REST Recommended

Everything nested under /api/projects/{id}. Project is the top-level resource.

# create a video project
POST /api/projects

# topics step
POST /api/projects/{id}/topics/generate
POST /api/projects/{id}/topics/{t}/approve

# script step
POST /api/projects/{id}/script/generate
POST /api/projects/{id}/script/approve

# get full project state
GET /api/projects/{id}
  • Clear ownership
  • GET project = full status
  • Resume any step naturally
  • Longer URLs
  • More nesting to navigate
B — Flat + project_id in Body

Short, flat URLs. project_id passed in request body or query string.

# create a video project
POST /api/projects

# topics step
POST /api/topics/generate
body: {"{ project_id }"}
POST /api/topics/{id}/approve

# script step
POST /api/scripts/generate
body: {"{ project_id }"}
POST /api/scripts/{id}/approve

# get full project state
GET /api/projects/{id}
  • Short, clean URLs
  • Easy to call standalone
  • project_id buried in body
  • Less obvious ownership
C — Hybrid (project root + flat steps)

Project for state management. Steps are flat but scoped by query param. Utilities (music, analytics) are always flat.

# project management
POST /api/projects
GET /api/projects/{id}/status

# pipeline steps (flat + ?project_id=)
POST /api/topics/generate?project_id=
POST /api/scripts/generate?project_id=
POST /api/footage/search?project_id=

# standalone utilities (no project needed)
GET /api/music/options
GET /api/analytics/{video_id}
  • Flat URLs for steps
  • Utilities work without project
  • Mixed conventions
  • project_id in query = awkward
