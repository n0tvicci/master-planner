3 Pipeline Architecture Approaches

How the pre-edit and post-edit scripts are structured internally. All 3 produce the same user experience: one command to run each phase.

A

Monolithic scripts

pipeline.py and publish.py each contain all logic inline — no separate tool files. Fast to build, easy to read start-to-finish.

Pros

  • Only 2 files to maintain
  • Simple to read top to bottom

Cons

  • If ElevenLabs fails mid-run, you re-run everything including the Claude API calls (costs money)
  • Can't test or fix one step without running the whole script
B

Stage-checkpointed pipeline

pipeline.py tracks progress in .tmp/<job-id>/state.json. Each stage writes its output before advancing. If anything fails, re-running resumes from exactly where it stopped — no duplicate API calls.

Pros

  • Safe to re-run after any failure
  • No wasted API credits on retries
  • Job folder is a self-contained asset bundle

Cons

  • Slightly more orchestration code
C

WAT-native decomposition (Recommended)

Each of the 9 pre-edit steps is its own tool script in tools/. pipeline.py is a thin orchestrator that calls them in order, with checkpointing built in. publish.py follows the same pattern for the post-edit steps.

Pros

  • Matches WAT architecture you're already using
  • Each tool is independently testable and fixable
  • You can run python tools/generate_voiceover.py --job abc to regenerate just one asset
  • Errors are isolated — a bug in footage search doesn't touch script generation

Cons

  • More files (~10 tool scripts vs 2)
