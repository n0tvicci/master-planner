Data Flow v4 — Post-Review Final

All review fixes applied: IN_PROGRESS status · scripts_run tracking · 120s poll cap · FAILED error storage · API Key auth · DLQ Alarm · NinjaOne script contract

PHASE 1 — INCIDENT INITIATION
1 IT Admin submits (API Key header required): POST /analyze → { device_name: "WIN-PC-0042", problem: "Adobe CC installation keeps failing with error 1603" }
2 Orchestrator Lambda generates incident_id, writes status: PENDING, scripts_run: [] to DynamoDB, enqueues job to SQS (VisibilityTimeout: 5400s)
3 UI immediately receives { incident_id, status: "PENDING" } — no waiting. UI polls DynamoDB for status updates.
PHASE 2 — AGENT INVOCATION
4 Worker Lambda picks up SQS message → sets status: IN_PROGRESS in DynamoDB → calls Bedrock Agents InvokeAgent:
{ agentId, agentAliasId, sessionId: incident_id, inputText: "Device: WIN-PC-0042. Problem: Adobe CC error 1603." }
5 Bedrock Agent starts reasoning. Auto-queries attached Knowledge Base for similar past incidents and known error 1603 fixes. These are injected into context automatically. Agent may run at most 4 diagnostic scripts.
🔄 PHASE 3 — BEDROCK AGENT ORCHESTRATION LOOP (managed by AWS, max 4 tool calls)
A Agent decides it needs installation logs first → invokes Action Group:
run_ninja_script({ script_name: "get_install_logs", device_name: "WIN-PC-0042", incident_id: "INC-..." })
B Action Group Lambda executes:
1. Lookup device ID from DynamoDB cache (or live NinjaOne API fallback)
2. Generate pre-signed S3 PUT URL for output path
3. Read scripts.json from S3 → inject output_url + incident_id as params
4. POST /v2/device/{id}/script/run → receives job_id
5. append_script_run(incident_id, "get_install_logs") → DynamoDB scripts_run list
6. Poll get_job_status(job_id) → (status, message) with exponential backoff · max 120s
7. On SUCCESS → read output.txt from S3 → return to Agent
   On FAILED → return "FAILED: {message}" (single API call — no double fetch)
   On timeout → return "timed out after 120s"
C Agent receives log output → finds MSI error 1603 + preceding network timeout → decides to investigate connectivity:
run_ninja_script({ script_name: "check_connectivity", device_name: "WIN-PC-0042", incident_id: "INC-..." })
D Action Group Lambda repeats steps B above → scripts_run now ["get_install_logs", "check_connectivity"] → returns: "Port 443 to adobe.com BLOCKED"
E Agent has enough data (used 2 of 4 allowed tool calls) → issues final structured response. Bedrock Agents saves full session under sessionId = incident_id.
PHASE 4 — REPORT + FOLLOW-UP
6 Worker Lambda receives Agent response stream → stores final report in DynamoDB → updates status: COMPLETE.
On exception: sets status: FAILED with analysis_report: "Analysis failed: {error}" — IT Admin sees the error, not a blank record.
7 UI displays full report to IT Admin: root cause, evidence, scripts run (from scripts_run list), KB matches, numbered recommended steps.
8 Follow-up question — IT Admin types: "Could it also be an SSL certificate issue?"
POST /followup/{incident_id} → InvokeAgent({ sessionId: incident_id, inputText: "Could it also be an SSL cert issue?" })
Agent has full prior context from its session store — no re-analysis needed, it continues the conversation.
9 IT Admin acts manually on fix steps. After resolution → uploads fix summary to s3://org-log-analysis/knowledge-base/incidents/ → S3 event triggers KB Ingestion Lambda → AOSS vector store updated → future analyses benefit.
⚠️ FAILURE PATH — SQS DLQ + MONITORING
F1 Worker Lambda crashes 3 times on same message → SQS moves message to Dead Letter Queue. Incident stays PENDING or IN_PROGRESS in DynamoDB.
F2 CloudWatch Alarm fires within 5 minutes (DLQ depth ≥ 1) → SNS Topic → email / Slack alert to on-call IT Admin for manual review.
F3 SQS VisibilityTimeout = 5400s (6× Lambda timeout of 900s) — ensures a running Worker Lambda always finishes before SQS can re-deliver, preventing duplicate incident processing.
Incident status lifecycle:
PENDING → IN_PROGRESS → COMPLETE
                     ↘ FAILED (with error in analysis_report) UI can show meaningful state at every stage — no ambiguous "stuck on PENDING" when analysis is actively running.
NinjaOne script contract (required):
param([string]$output_url, [string]$incident_id)
$output = "... run diagnostics here ..."
$bytes = [Text.Encoding]::UTF8.GetBytes($output)
Invoke-WebRequest -Uri $output_url -Method PUT -Body $bytes Scripts that don't upload to S3 via the presigned URL will produce empty output → poller times out → Agent gets "timed out after 120s" instead of real data.
Timing budget (worst case):
4 scripts × 120s poll = 480s
+ Agent reasoning overhead ≈ 60s
+ Bedrock invocation overhead ≈ 30s
Total ≈ 570s << 900s Lambda limit Comfortable headroom. SQS VisibilityTimeout 5400s means no re-delivery before Lambda finishes.
