Section 2 — Detailed Data Flow

Step-by-step from trigger to analysis result, including async handling and conversation loop

PHASE 1 — INCIDENT INITIATION
1 IT Admin submits: { device: "WIN-PC-0042", problem: "Adobe CC installation keeps failing with error 1603" }
2 API Gateway validates + forwards to Orchestrator Lambda
3 Lambda generates incident_id = INC-20260521-WIN-PC-0042-001, stores initial record in DynamoDB with status PENDING
4 Lambda calls NinjaOne API → triggers diagnostic script execution on target device
5 Lambda returns { incident_id, status: "COLLECTING_LOGS" } to UI immediately — no waiting
PHASE 2 — LOG COLLECTION (ASYNC)
6 NinjaOne script runs on device: collects Windows Event Viewer exports, MSI installer logs, Windows Update logs, application crash dumps as needed
7 Script uploads files to S3: s3://org-log-analysis/logs/WIN-PC-0042/INC-20260521-001/system.evtx
8 S3 event notification (or NinjaOne webhook callback) triggers → SQS message enqueued: { incident_id, device, problem, s3_prefix }
PHASE 3 — AI ANALYSIS
9 Worker Lambda picks up SQS message → fetches all log files from S3 → chunks large files (logs can be huge)
10 Lambda queries Bedrock Knowledge Base with problem description → retrieves top-K relevant documents (past incidents, known error codes, fix guides)
11 Lambda calls Bedrock Converse API with: system prompt + problem context + log content + KB results
12 Claude returns structured response: root cause → evidence from logs → KB matches → recommended steps (numbered)
13 Lambda saves full conversation history + result to DynamoDB → updates incident status to ANALYSIS_COMPLETE
PHASE 4 — HUMAN REVIEW + OPTIONAL FOLLOW-UP
14 UI polls for status or receives webhook → displays full analysis report to IT Admin
15 [Optional] IT Admin types follow-up: "What if it's a group policy conflict instead?" → API Gateway → Lambda loads session from DynamoDB → Converse API continues same session → new answer appended
16 IT Admin acts manually on recommended steps. After resolution, admin can mark incident resolved + optionally save the fix to the Knowledge Base for future use.
Key design decisions:
  • Async by default — UI gets an incident ID immediately; analysis runs in the background. No timeout risk.
  • SQS as buffer — during Patch Tuesday spikes, jobs queue up cleanly. Worker Lambda scales out independently.
  • KB queried before Bedrock — similar past incidents + known fix docs are injected into the prompt, grounding the AI in your org's actual history.
  • Session in DynamoDB — each incident has a full conversation thread. Follow-up questions have full prior context.
  • Human closes the loop — resolved fixes can be fed back into the KB, making the system smarter over time.
