Data Flow v3 — Bedrock Agents (Final)

Exact step-by-step flow using AWS Bedrock Agents with Action Groups and NinjaOne script execution

PHASE 1 — INCIDENT INITIATION
1 IT Admin submits: POST /analyze → { device: "WIN-PC-0042", problem: "Adobe CC installation keeps failing with error 1603" }
2 Orchestrator Lambda generates incident_id, writes status: PENDING to DynamoDB, enqueues job to SQS
3 UI immediately receives { incident_id, status: "PENDING" } — no waiting. UI polls for updates.
PHASE 2 — AGENT INVOCATION
4 Worker Lambda picks up SQS message → calls Bedrock Agents InvokeAgent:
{ agentId, agentAliasId, sessionId: incident_id, inputText: "Device: WIN-PC-0042. Problem: Adobe CC error 1603." }
5 Bedrock Agent starts reasoning. It auto-queries attached Knowledge Base for similar past incidents and known error 1603 fixes. These are injected into its context automatically.
🔄 PHASE 3 — BEDROCK AGENT ORCHESTRATION LOOP (managed by AWS)
A Agent decides it needs installation logs first → invokes Action Group:
run_ninja_script({ script_name: "get_install_logs", device_id: "WIN-PC-0042" })
B Action Group Lambda executes:
1. Reads scripts.json from S3 → finds get_install_logs entry
2. Fires: POST /v2/device/WIN-PC-0042/script/run with body:
{ "type": "ACTION", "id": 1087, "uid": "def456uvw", "parameters": "", "runAs": "SYSTEM" }
3. Waits for script completion → fetches output from S3 → returns to Agent
C Agent receives log output → finds MSI error 1603 + preceding network timeout → decides to investigate connectivity:
run_ninja_script({ script_name: "check_connectivity", device_id: "WIN-PC-0042" })
D Action Group Lambda fires: POST /v2/device/WIN-PC-0042/script/run → { "type": "ACTION", "id": 1042, "uid": "abc123xyz", "parameters": "", "runAs": "SYSTEM" } → returns: "Port 443 to adobe.com BLOCKED"
E Agent has enough data → issues final structured response. Bedrock Agents saves full session to its managed store under sessionId = incident_id.
PHASE 4 — REPORT + FOLLOW-UP
6 Worker Lambda receives Agent response → stores final report in DynamoDB → updates status to COMPLETE
7 UI displays full report to IT Admin: root cause, scripts run + findings, KB matches, numbered recommended steps
8 Follow-up question — IT Admin types: "Could it also be an SSL certificate issue?"
POST /followup/{incident_id} → InvokeAgent({ sessionId: incident_id, inputText: "Could it also be an SSL cert issue?" })
Agent has full prior context from its session store — no re-analysis needed, it continues the conversation.
9 IT Admin acts manually on fix steps. After resolution → optionally uploads fix summary to S3 → ingested into Knowledge Base for future incidents.
scripts.json in S3 — example entry shape:
{ "name": "check_connectivity",
  "description": "Tests DNS, gateway ping, port 443/80 to common endpoints. Use for network-related install or update failures.",
  "ninja_body": { "type": "ACTION", "id": 1042, "uid": "abc123xyz", "parameters": "", "runAs": "SYSTEM" } } Adding a new script = add one entry to scripts.json in S3. No Lambda redeployment. Agent picks it up on next invocation.
