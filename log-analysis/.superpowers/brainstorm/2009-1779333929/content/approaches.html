Three Architecture Approaches

Choose the foundation for your AI log analysis system

A

Direct Lambda + Bedrock Invoke

One-shot only. No conversation.

NinjaOne script → S3
S3 event → SQS → Lambda
Lambda fetches logs → builds prompt
Bedrock Claude (InvokeModel API)
Result → DynamoDB → API Gateway → You

Pros

  • Simplest to build
  • Cheapest to run
  • Fast delivery

Cons

  • No follow-up questions
  • No conversation memory
  • One answer, take it or leave it
B

Full Bedrock Agents

Agentic. Agent decides what to fetch and how.

IT Admin → API Gateway → Bedrock Agent
Agent has Action Groups:
  → fetch_logs (Lambda → S3)
  → search_knowledge_base
Agent orchestrates multi-turn
Native session memory built-in

Pros

  • Fully conversational
  • Agent decides which logs to fetch
  • Knowledge base for known fixes

Cons

  • Most expensive
  • Harder to control
  • Complex to set up correctly
C

Bedrock Converse API + Session State ⭐ Recommended

One-shot primary analysis + optional follow-up conversation.

NinjaOne → S3 (logs)
API Gateway → Lambda → SQS
Worker Lambda:
  → fetches + chunks logs from S3
  → Bedrock Converse API (multi-turn)
  → stores session in DynamoDB
Initial: full D-style analysis
Follow-up: ask questions same session

Pros

  • One-shot + conversation hybrid
  • You control the orchestration
  • Cheaper than full Agents
  • Scales easily with SQS
  • Session history per incident

Cons

  • Need to manage session state
  • More work than Option A
Why C is recommended: You need the one-shot primary analysis for speed (80% of cases), but the conversational follow-up for complex failures where the first answer isn't enough. Bedrock Converse API handles multi-turn natively without the overhead and cost of full Bedrock Agents. You keep full control of the orchestration logic, and SQS handles the scale of 1000+ devices cleanly.
